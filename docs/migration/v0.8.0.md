# Migrating to v0.8.0

## One fault shape

- Every service fault inventory entry classifies with `kind` (was
  `category`), typed to that service's own fault base. It is mandatory.
- `first-observed` is mandatory in inventory entries and on `fault-raised`
  and `fault-cleared`. Use the device's time when it reports one, otherwise
  the time you first saw the fault.
- A fault about one sub-component carries `component` with
  `component-class` and `component-id` (the key of the live-state entry; a
  composite key joined with `/`). Absent means the whole device. Stop
  encoding the sub-component inside `fault-id`.
- `fault-id` and `correlates-with` are limited to 128 characters.
- `fault-raised` may be re-emitted with the same `fault-id` as an upsert.
- Protobuf consumers: in every service `Fault` message the class moved from
  field `category` (tag 1, now reserved) to `kind` (tag 99). v0.8.0 decoders
  treat tag 1 in old stored or in-flight bytes as an unknown field, so
  re-encode or translate stored data.

## Cabinet-power faults

Signal-control and DMS publish cabinet-power faults with their own
identities (for example `openits-signal-control-types:sc-fault-cabinet-on-battery`),
which derive from the cabinet-power identity. Filter fleet-wide with
`derived-from-or-self(kind, 'openits-cabinet-power:cabinet-power-on-battery')`.
Conformance rejects a fault event whose `kind` is not a fault of the
subject's service.

## Health, freshness and modes

- **Health on every device root.** Each device root `state` now carries
  `oper-status`, `last-change` and `observed-at` (the `device-health`
  grouping). Absent `oper-status` means unknown, never ok.
- **One freshness name.** The reading timestamps `measured-at`,
  `collected-at`, `last-update` and `computed-at` are all renamed
  `observed-at`. Breaking: read `observed-at`.
- Protobuf consumers: each renamed timestamp moves to a NEW field number, and
  the old number and name are reserved. v0.8.0 decoders treat the old field
  in stored or in-flight bytes as unknown, so re-encode or translate stored
  data. The moves: perception `ZoneOccupancyZonesZone` 6 to 8; signal-control
  `Measurement` 5 to 6; ramp-metering detector readings (two messages) 4 to 8;
  reversible-lane gate state 1 to 8; RSU `SampleBasis` 5 to 6.
- **`comm-lost` carries evidence.** It must carry `last-contact` and
  `observed-by`. Live state for that device is stale as of `last-contact`;
  a reading is current again only when its `observed-at` is later than that
  `last-contact` (see "Comm-loss staleness" in
  `docs/data-model.md`).
- **Mode values derive from their family's base.** A `mode-changed` `mode`
  and `previous-mode` must derive strictly from the base named by the
  `openits-types:mode-value-base` on its `kind`. Conformance rejects a
  mismatch and `make check-mode-kinds` gates fixtures. DMS's kind is bound to
  `sign-mode`, so a DMS control-mode takeover no longer rides `mode-changed`;
  it will move onto `control-source` (which `mode-changed` carries) when the
  DMS cut moves `control-mode` there.
- **Bare `mode-unknown`.** `openits-types:mode-unknown` is valid under a
  family kind only through that family's own dual-based unknown (DMS and ramp
  metering today). Emit the family's identity, not the bare one.

## Signal control: live operating state

`signal-controller/operation` now carries one independent fact per leaf
(including `cabinet-output-since`, when the displays last changed),
and the cabinet monitor reports whether it was read.

| Before | After |
|---|---|
| `mode` = `mode-flash` | `cabinet-output` = `flash` (+ `flash-cause`) |
| `mode` = `mode-off` | `cabinet-output` = `dark` |
| `mode` = `mode-manual` | `control-source` = `openits-types:control-manual` |
| `mode` = `mode-preempt` | `preempt-active` = true |
| `mode` = `mode-priority` | `priority-active` = true |
| `flash-active` | `cabinet-output` = `flash` |
| `last-mode-change` | `mode-since` (coordination-mode changes only); entry into flash or dark is `cabinet-output-since` |
| `flash-cause` `flash-mmu-conflict` | `flash-monitor` |
| `flash-cause` `flash-fault-monitor` | `flash-controller-fault` |
| monitor: absent `fault-type` meant no fault | `monitor/status` (`unknown`, `ok`, `fault`, `not-read`, `not-equipped`); `fault-type` only when `status` is `fault` |

`mode` now holds only `mode-coordinated`, `mode-free` or the new
`openits-signal-control-types:mode-unknown`. A coordinated controller
under monitor flash reports `mode-coordinated` with `cabinet-output`
`flash`. `preempt-active` and `priority-active` summarise the preemptor
and active-request lists. In protobuf, the `Operation` fields
`flash_active` (2) and `last_mode_change` (5) are removed and their
numbers and names reserved.

Events:

- New `cabinet-output-changed` (`previous-cabinet-output`,
  `cabinet-output`, `flash-cause`) fires when the displays change.
  Producers that signalled flash with a `mode-changed` to `mode-flash`
  emit this instead.
- A change of control authority (for example manual takeover, or a fall
  to local backup) is reported as `mode-changed` with an unchanged `mode`
  (equal to `previous-mode`) and the new `control-source`. Producers that
  sent `mode-changed` to `mode-manual` send this instead.
- `operational-status-report` uses the shared status summary
  (`oper-status`, `control-source`, `uptime-s`, `active-fault-count`)
  plus `cabinet-output`, `flash-cause`, `mode`, `preempt-active`,
  `priority-active`, `monitor-status`, `mode-since`,
  `cabinet-output-since`. `flash-active`, `last-mode-change` and `uptime-seconds` are removed; in protobuf their
  field numbers (10, 4, 5) and names are reserved.
- `tsam-mode-changed` `prior`/`current` are renamed
  `previous-mode`/`mode`; protobuf reserves the old numbers (2, 3) and names.
